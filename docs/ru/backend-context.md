# Backend context

Язык: **Русский** · [English](../en/backend-context.md)

Статус: актуальный архитектурный контекст backend на 2026-08-01.

Этот документ фиксирует уже принятые решения и границы модулей. Детали,
которые ещё не спроектированы, помечены как планируемые и не должны
восприниматься как готовый контракт.

## Назначение продукта

OpenAPI Creator Studio — визуальный редактор OpenAPI-документов. Пользователь
собирает API через формы: создаёт пути и операции, параметры, схемы, тела
запросов, ответы, примеры, серверы и security-настройки. Редактор должен
показывать структуру документа, ошибки и документационный preview, а также
позволять импортировать и экспортировать OpenAPI.

Текущий приоритет — корректная backend-модель редактора. Она должна позволять
изменять документ небольшими операциями и не привязывать доменную логику к
YAML, JSON, HTTP, Spring или конкретному хранилищу.

## Модули

| Модуль | Ответственность | Текущее состояние |
| --- | --- | --- |
| `studio-core` | Модель документа в памяти, создание, навигация, ссылки, семантическая валидация и команды редактирования | Реализуется и покрыт тестами |
| `studio-openapi` | Преобразование OpenAPI YAML/JSON в нормализованную core-модель и обратно, а также version-specific проверки | Реализованы строгие end-to-end импорт и экспорт OpenAPI 3.1 с round-trip тестами |
| `studio-app` | Spring Boot composition root, REST API, application services и подключение инфраструктуры | Реализованы и покрыты HTTP-интеграционными тестами API-first REST-контракт, in-memory workspace, lifecycle документов, команды, валидация, экспорт и единые Problem Details |

Зависимости направлены внутрь:

```text
studio-app -> studio-openapi -> studio-core
           -> studio-core
```

`studio-core` ничего не знает о двух внешних модулях.

Подробная архитектурная документация:

- [architecture/openapi.md](architecture/openapi.md);
- [architecture/app.md](architecture/app.md).

## Стратегия версий OpenAPI

Для первого релиза целевая версия и значение по умолчанию — OpenAPI `3.1.2`.
Текущий core-валидатор выбирает семантические правила для семейства `3.1.x`.
Строгие parsing YAML/JSON, структурная валидация, version-specific маппинг,
семантическая валидация и serialization соединены конвейерами импорта и
экспорта. Детектор проверяет и читает `major.minor.patch`; поддержка
определяется при выборе адаптера.

Архитектура рассчитана на последующее добавление `3.0.x` и `3.2.x`:

1. Core хранит нормализованное представление документа.
2. Адаптер конкретной версии преобразует синтаксис этой версии в core-модель.
3. При экспорте адаптер преобразует core-модель в допустимый синтаксис выбранной
   версии и сообщает о данных, которые нельзя выразить без потерь.
4. Структурная проверка по официальной схеме OpenAPI выполняется в
   `studio-openapi`; проверки связей и смысла документа — в `studio-core`.

Core-модель представляет согласованное надмножество нужных нам возможностей,
включая известные поля OpenAPI 3.2, например `Tag.parent`, `Tag.kind` и
`OpenApiDocument.self`. Наличие таких полей не означает, что поддержка 3.2 уже
готова. Для более старой версии они могут отсутствовать, а адаптер решает,
допустимо ли их сериализовать.

Различия версий нормализуются на границе. Например:

- `nullable: true` из OpenAPI 3.0 в core представляется типами `STRING` и
  `NULL`;
- schema examples в core хранятся коллекцией;
- version-specific ограничения не должны расползаться по доменным моделям.

## Сохранение неизвестных данных

Редактор не должен молча терять расширения или пока не поддержанные поля.
Наследники `ExtensibleObject` содержат `additionalFields`, а
`SchemaDefinition` — `additionalKeywords`. Значения представлены через
`DocumentValue`.

Адаптер формата обязан помещать неизвестные значения в эти контейнеры и
возвращать их при сериализации, если целевой формат это допускает.

## Редактирование документа

Документ в `studio-core` — изменяемый граф объектов в памяти. Пользовательские
действия должны выражаться через небольшие `DocumentCommand`, а не через
произвольное изменение модели на REST-границе.

Команда:

- знает, какое изменение выполняет;
- получает `CommandContext` с документом, навигатором и индексом `$ref`;
- сначала проверяет ожидаемые причины отказа;
- либо атомарно изменяет документ и возвращает изменённые пути, либо возвращает
  структурированные issues.

Application layer в будущем будет отвечать за загрузку документа, транзакцию,
авторизацию, конкурентное редактирование и сохранение результата. Эти
обязанности не входят в core.

## Валидация

Проверки разделены на два уровня:

- `studio-openapi`: разбор YAML/JSON и соответствие структуре выбранной версии
  OpenAPI;
- `studio-core`: семантические правила, которым нужен связный граф документа —
  уникальность, корректность `$ref`, path templates, security requirements,
  links, callbacks, encoding, discriminator и servers.

Невалидное промежуточное состояние документа допустимо во время визуального
редактирования. Валидация сообщает issues, но не является механизмом мутации.
Команды отклоняют только действия, которые нельзя безопасно или однозначно
выполнить.

Импорт строже интерактивного редактирования. Любая ошибка parsing,
структурной проверки, mapping или семантики приводит к `ImportFailure`, и
документ не возвращается. Warnings импорт не блокируют.

## Хранение и размер документа

В первом релизе весь документ находится в памяти. Core не содержит repository,
ORM и других persistence abstractions. Хранилище подключается снаружи и может
меняться без изменения доменной модели.

Переход к частичной загрузке, базе данных или графовому хранилищу не является
текущим решением. Он рассматривается только после измерения реальных проблем с
размером документов, временем обхода или индексирования ссылок.

## Граница с frontend

Планируется отдельный React-интерфейс. В production его статическая сборка может
раздаваться Spring Boot приложением, но JavaScript всё равно выполняется в
браузере и обращается к backend через REST API. Контракты REST и application
services пока не зафиксированы.

## Что уже есть в `studio-core`

- полная базовая модель OpenAPI-документа и произвольных document values;
- фабрика нового документа;
- адресация через JSON Pointer и обход графа;
- разрешение локальных `$ref`, индекс usages и безопасное обновление ссылок;
- набор семантических правил OpenAPI 3.1;
- команды для components, schemas, paths и operations;
- модульные тесты этих подсистем.

## Отложенные решения

- формат REST API и DTO;
- document sessions, сохранение и конкурентное редактирование;
- undo/redo и история команд;
- force-удаление объектов с активными ссылками;
- оптимизация индексов для очень больших документов;
- детализация поддержки OpenAPI 3.0 и 3.2.

Когда соответствующий модуль будет спроектирован, для него следует создать
отдельный документ в `docs/architecture/`, а здесь оставить только обзор и
ссылку.

# Архитектура `studio-app`

Язык: **Русский** · [English](../../en/architecture/app.md)

`studio-app` — Spring Boot composition root и прикладной слой. Он публикует REST API,
координирует `studio-core` и `studio-openapi` и подключает заменяемые инфраструктурные
адаптеры.

## REST-контракт

REST API проектируется contract-first. Его документ OpenAPI 3.1 находится в
`studio-app/src/main/resources/static/openapi/studio-api.yaml`. OpenAPI Generator создаёт
API-интерфейсы и транспортные модели в `build/generated/openapi`; это артефакты сборки,
которые не коммитятся. Ручные контроллеры реализуют сгенерированные интерфейсы.

Сгенерированные транспортные типы не используются в `studio-core`. Прикладной слой явно
преобразует generated DTO в core-типы и обратно. Транспортные мапперы используют MapStruct
как Spring-компоненты с constructor injection; HTTP-статусы и заголовки формируются в
контроллерах.

## Workspace документов

`DocumentWorkspace` — прикладной порт, владеющий открытыми сессиями редактора. Сессия
содержит UUID, неотрицательную revision и один изменяемый граф `OpenApiDocument` из core.
Начальная revision равна `0`.

В первом релизе используется `InMemoryDocumentWorkspace`. Порт создаёт, находит и удаляет
сессии, а также атомарно выполняет `DocumentCommand` над документом. Для команд применяется
optimistic concurrency:

- переданная revision должна совпадать с текущей;
- успешная core-команда увеличивает revision ровно на один;
- отклонённая core-команда не изменяет revision;
- устаревшая revision приводит к `RevisionConflictException` до выполнения команды.

Команды каждого сохранённого документа выполняются последовательно и независимо от других
документов. Concurrent map защищает только коллекцию сессий. Workspace получает владение
документом, переданным в `create`; вызывающий код не должен изменять этот граф в обход
workspace.

Порт не привязан к способу хранения. В будущем persistent-адаптер сможет реализовать те же
операции через транзакции БД или распределённый optimistic locking без изменения REST-
контракта и core-модели.

Операции чтения используют `DocumentWorkspace.inspect`. Callback инспекции выполняется
под той же блокировкой документа, что и команды, поэтому наблюдаемая revision и результат,
полученный из документа, относятся к одному согласованному снимку. Callback не должен
сохранять или раскрывать изменяемый граф документа.

## Жизненный цикл документа

Первый application-срез реализует сгенерированный контракт `DocumentsApi`.
Он создаёт пустые документы OpenAPI 3.1, строго импортирует YAML или JSON,
возвращает текущее стандартное JSON-представление и закрывает сессии документов.

`DocumentLifecycleService` координирует core-фабрику документа, OpenAPI-импортёр
и `DocumentWorkspace`. `DocumentRepresentationService` использует адаптер версии
без полного export-конвейера, поэтому UI может получить даже промежуточное
состояние редактора. REST-маппинг и преобразование диагностик остаются в web-слое.

Создание и импорт возвращают revision `0`, `Location` и строгий ETag с revision.
Для закрытия требуется та же revision в `If-Match`; проверка и удаление выполняются
атомарно внутри in-memory workspace.

## Диспетчеризация команд

Сгенерированный полиморфный `DocumentCommandRequest` обрабатывается реестром
типизированных компонентов `DocumentCommandRequestHandler`. Каждый handler преобразует
ровно один класс REST-запроса в core-команду `DocumentCommand`; добавление команды не
требует изменения dispatcher. Дублирующиеся регистрации отклоняются при запуске.

`DocumentCommandService` выполняет построенную команду через `DocumentWorkspace`.
Успешный результат содержит новую revision и изменённые пути JSON Pointer. Отклонённая
core-команда не меняет revision и преобразуется в Problem Details с кодом `409` и
структурированными command issues. Для отсутствующей сессии и устаревшей revision
используются общие ответы `404` и `412`.

## Ручная валидация

`DocumentValidationService` запускает core-компонент `DocumentValidator` через инспекцию
workspace. Валидация не изменяет документ и не увеличивает revision. REST-ответ содержит
эту revision, общий признак валидности и семантические диагностики; та же revision
возвращается в виде строгого ETag.
